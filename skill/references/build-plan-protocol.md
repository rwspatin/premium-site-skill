# Reference → build plan protocol (Altra Labs M2-A5)

Using a reference well means knowing what to REJECT. Beautiful extras (another slider, another
video, another visual logic) add complexity without serving the story — cut them.

## The 3-question test (per section of any reference)
1. **Why does this work?** (name the mechanism, not the look)
2. **Does it help THE story?** (yours, not theirs)
3. **Do I really need it in this project?**
Only a triple yes survives. "The reference had it" is never a reason.

## From idea to block
Translate every accepted idea into a nameable block: hero · intro · grid · split section ·
gallery · testimonial · CTA · ledger/list · marquee. If you can't name it, you can't build it.
Take ONE structure per reference; never import a new visual logic mid-page.

## The build plan
An ordered list of sections, each with ONE clear function, e.g.:
1. Hero — sets tone, main message, primary action
2. Intro — personality and context
3. Grid — offers/services, scannable
4. Split — depth: values/process/differentiator; a pause in the page rhythm
5. CTA — strong message, small support text, single action
End state for the reader: who you are · what you offer · why trust you.
When every section has a function and the extras are gone, the reference stops being
inspiration and becomes an executable plan.

## Worked audit: profissional_site home (2026-09-03)
Hero(quem sou+ação) → Números(prova) → Serviços(oferta) → Depoimento(confiança) →
Resultados(prova profunda) → Projetos(obras) → Trajetória(história) → Blog(pensamento) →
CTA(ação). Function check passed for all 9; the failure was LENGTH, not presence:
Resultados listava 8 casos (~5 telas) no meio da home — prova profunda virou monotonia.
Fix: top 4 na home + "ver todas no currículo" (a lista completa já vive lá). Rule extracted:
**on the home, every list section shows its best 3–4 and links to the full set.**
